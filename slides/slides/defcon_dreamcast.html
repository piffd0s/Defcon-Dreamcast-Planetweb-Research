RCE on the Sega Dreamcast PlanetWeb Browser

Christopher Hernandez

Saturday 10:45 AM · LVCC Level 1 · Exhibit Hall West 3 – 801

Why this target

The first mainstream internet-connected console

  • Launched September 9, 1999 (9/9/99)
  • Shipped with a 56k modem in every unit — online out of the box
  • A web browser on your TV, a decade before smart TVs
  • Online multiplayer before Xbox Live existed

Discontinued March 31, 2001. Sega's last console.

Personal connection

This was the first console I played as a kid — probably too much. I used that 56k modem to dial up to game servers. 25 years later, I wanted to understand what was actually happening on the other end of that phone line.

Why a year-2000 browser

Lower barrier to entry than modern browsers

  • No ASLR — every address is deterministic, boot to boot
  • No W^X / DEP — memory is read-write-execute everywhere
  • No sandbox — the Java VM has no SecurityManager installed
  • No code signing — downloaded JARs run without verification
  • Plaintext HTTP — no TLS anywhere

Every modern mitigation you fight in Chrome/Safari — absent. The trust model is "if we fetched it, run it."

But there are constraints

  • Exotic CPU — Hitachi SH-4 (SuperH), not x86/ARM
  • 16 MB of RAM — total, shared with video and the OS
  • Usable memory ~10 MB — the browser image is 4.4 MB; video, stack, and system structures claim the rest
  • Flat memory — no MMU page tables, no heap metadata to abuse
  • PersonalJava 1.1.8 — a stripped JDK from 1998; AWT 1.1 only

The target

  • SoftwarePlanetWeb Internet Browser v3.0 (USA) — GD-ROM disc
  • DeveloperPlanetWeb, Inc. (San Jose, CA) — defunct
  • CPUHitachi SH-4 @ 200 MHz, little-endian, 32-bit RISC
  • RAM16 MB flat — no MMU, no ASLR, no DEP
  • Main binary1ST_READ.BIN — 4.4 MB, loaded at 0x8C010000
  • Java runtimePersonalJava 1.1.8, class format v45.3
  • Online service"Eden" framework → eden.planetweb.com (dead since ~2003)
  • Network56k modem (built-in) / broadband adapter (optional)

The browser dials up, fetches code from a server that no longer exists — whoever answers for that domain owns the console.

Reverse engineering challenges

GD-ROM extraction

The Dreamcast uses a proprietary disc format (GD-ROM). Game data lives in a high-density area at LBA 45000. The ISO9660 stores absolute sector addresses — every read must subtract the track's start LBA. Standard ISO tools break on it.

Wrote a custom extractor (extract_dreamcast.py) to handle GDI rips correctly.

IDA Pro + SH-4

Open 1ST_READ.BIN in IDA — it has no idea what it's looking at. No headers, no entry point hints. You have to:

  • Select the SH-4 processor module (Hitachi SuperH)
  • Set the load address to 0x8C010000
  • Point the entry at the first instruction (SR setup / nop sled)

Luckily IDA 9.x has a working SH-4 decompiler — Hex-Rays output is readable.

Java decompilation

The browser bundles a full Java runtime (classes.zip). Decompiled all PlanetWeb/Eden/OpenBrew packages to understand the service-loading chain, the native bridge, and the trust model. The class format is v45.3 — modern decompilers handle it, but you must compile against the device's own classes.zip, not a standard JDK.

Research

attack surface mapping & chain identification

Attack surface map

Eden service framework

Auto-login, discovery, subscription, JAR download + execution. All plaintext HTTP. No signing. No sandbox.

Design-level RCE if you control DNS

Java→native bridge

27 native commands via sendCommand(int, Object, Object). Flash writes, VMU file ops, URL navigation, device-ID get/set.

Memory corruption primitives in handlers

Native parsers

Image decoders (JPEG, GIF, PNG), MIME attachment parser, HTML renderer. All native SH-4, no bounds checking culture.

Stack/heap overflows, decoder hangs

Mail client

Full POP3/SMTP client. MIME parsing happens in native code. Attachment name= parameter → unbounded stack copy.

VMU / peripheral I/O

File read/write to Visual Memory Unit. Filename + content from attacker bytes. Path/length validation absent.

Attack chain mapping

Two viable paths to native code execution — we use both.

Path A: Design-flaw RCE (foothold + transport)

1 Answer DNS for eden.planetweb.com
↓
2 Serve rogue Eden login → discovery → subscribe
↓
3 Console downloads + runs our JAR (privileged)

100% reliable. Zero corruption. Our foothold.

Path B: Memory corruption (pivot to native)

4 Java calls setRawDeviceID(byte[]) via bridge
↓
5 Unbounded memcpy plants stub at fixed address
↓
6 Email overflow → saved PR = stub → native exec

Deterministic. No spray, no sled.

Findings

6 vulnerabilities · 389 unique crashes

Bug #1 — Eden service-subscription RCE critical

boot → Eden login → discovery URL (server XML) → subscribe
→ service JAR URL (server-controlled) → download over plaintext HTTP
→ read Main-Class → JarClassLoader.newInstance().run()

  • No SecurityManager is ever installed — loaded code is fully privileged
  • No JAR signature check anywhere in ServiceManager
  • All comms plaintext HTTP to a dead domain
  • Jar-Files: manifest attr pulls additional JARs from arbitrary URLs

Impact

Anyone who answers DNS for eden.planetweb.com ships a JAR the console downloads and runs — arbitrary privileged code, no interaction, no corruption.

The domain has been dead for 20+ years. It's free real estate.

Bug #2 — MIME name= stack overflow high

  • Mail client handler fn_application_x_dreamcas @ 0x8C04669C
  • MIME attachment name= parameter copied unbounded into a 64-byte stack buffer
  • Overwrites saved return address (PR register) → full SH-4 PC control
  • Byte constraints: copy terminates on 0x00, 0x20 (space), 0x22 (quote) — payload avoids them

An email that, when opened, gives us native code execution.

This is the pivot from the Java sandbox to bare-metal SH-4.

Bug #3 — setRawDeviceID unbounded memcpy high

The Java→native bridge command 100 (handler @ 0x8C04E0DC):

memcpy(dst=0x8C29ABE6 [FIXED], src=attacker byte[], len=attacker)

The device-ID field is 8 bytes. Length comes from the VM array marshalling — no bound check.

What this gives us

  • Linear write of attacker-controlled bytes to a fixed, known address
  • Reachable directly from our privileged Java code
  • Not just a crash — a controlled placement primitive

BSS neighbors

  • +0x08 state flag (12 refs, byte load/store)
  • +0x42 IM object pointer (32 refs, virtual-called)
  • +0x76 error-code switch base (50 refs)

Remember this primitive. It solves the hardest problem in the chain.

Bonus bugs — image parser crashes DoS / ACE leads

An in-browser fuzzer (mutated images served at unique URLs to bypass the VMU page cache) found 78 faults + 279 hangs across 389 unique crashes:

GIF LZW

Min code size = 12 (valid: 2–8) → decoder infinite loop. 35-byte PoC.

Progressive JPEG

SOF2 component count Nf=5 (max 4) → component-array OOB → hang.

GIF dimensions

65535 × 65535 logical screen → allocation/loop hang.

All reachable by a served image alone — no Java needed. The JPEG and GIF faults are strong memory-corruption leads; shipped here as confirmed DoS.

The Chain

from DNS query to native DOOM

The full exploit chain

DNS MITM eden.planetweb.com → Eden subscription RCE → privileged Java
→ chunked-stage doom+WAD into the heap (32 KB chunks, 3.8 MB total)
→ plant SH-4 stub @ 0x8C29ADE8 via setRawDeviceID memcpy
→ craft + send the DOOM-STAGE email → MIME stack overflow
→ saved PR = 0x8C29ADE8 → stub scans heap for magic → copies doom+WAD
→ native SH-4 DOOM, live on the Dreamcast

Reliable. Reproducible. One command to launch.

Challenge #1 — the overflow was a coin flip

  • Fixed payload, fixed saved-PR value — yet ~50% of opens crashed
  • The stack location at trigger time varies by ~32 KB depending on browser call depth / JVM state
  • A hardcoded PR → an on-stack NOP sled is a gamble: half the time it clobbers a live pointer → 0x60036003 fault loop
  • No clean jmp @r15 or stack-pivot gadget exists in the 4.4 MB binary

~50%

reliable, at best

Unacceptable for a live demo.

Challenge #1 — the fix

Don't fight the random stack. Put the code at a fixed address.

Java (reliable) → setRawDeviceID(100) plants 366-byte SH-4 stub at 0x8C29ADE8
Overflow → saved PR = 0x8C29ADE8 · no sled, no stack dependence

A "bug" (no bounds check) became our reliability mechanism.

Deterministic every time. The unbounded write fixes the random stack.

Challenge #2 — don't kill the browser while planting

  • The memcpy destination overlaps an IM-list head pointer at DST+0x46
  • Zero it → interface manager dereferences null → crash before the overflow even fires
  • Can't read it back to preserve it — getRawDeviceID only returns 8 bytes

Fix

Write a harmless fake node whose teardown-unlink targets scratch memory. Plant last (after staging the payload) to minimize the survival window. Browser stays alive; mail UI keeps working.

Challenge #3 — getting 3.8 MB onto 16 MB of RAM

The email can't carry it

  • Mail attachment parser is O(n²) — a big body hangs
  • So Java stages doom.bin + WAD over HTTP into one heap byte[]
  • The native stub scans the heap for a magic tag, copies it into place

The network fights back

  • A single 3.4 MB URL.openStream() hangs the net thread → "PlanetWeb offline"
  • PersonalJava 1.1.8: no setRequestProperty (no HTTP Range), close() won't unblock a hung read
  • Fix: chunked transfer — 32 KB pieces via ?start=N&len=M
  • Write the magic tag last → scanner only finds a complete blob

Challenge #4 — actually making DOOM run

Memory tetris

WAD @ 0x8C450000, engine @ 0x8CC00000, heap @ 0x8C790000. Non-overlapping, manually laid out in 16 MB. Trim audio lumps from the WAD — keep PNAMES/textures/levels or R_Init dies.

Video

No KOS — reuse the browser's live video. Live-read FB_R_SOF1 for the real framebuffer address. Hardcoding it rendered off-screen ("frozen browser"). 2× scale 320×200 → 640×480.

Timing

Drive the game loop off SH-4 TMU2 free-running counter — no interrupts needed, just poll the decrementer.

Boot state

Clear SR.BL, mask IRQs, inherit the browser's machine state, then jump in. Sound disabled (audio lumps trimmed from WAD).

16 MB memory layout

Constraints

  • 16 MB total — doom+WAD (~3.8 MB) must tetris around a live 4.4 MB browser
  • No ASLR — every address above is fixed … except the stack
  • The stack varies ±32 KB at trigger time → the reliability problem
  • The planted stub lands at a fixed BSS address via the memcpy primitive
  • WAD, engine, heap: all at addresses we chose to avoid overlap
Debugging

how we saw inside a black box

Debugging with the Dreamcast emulator

Custom Flycast build

  • Built Flycast from source with the GDB stub enabled
  • Added a patch that dumps SH-4 fault context on every exception: epc, PR, SR.BL, r15 (stack pointer)
  • DOOM writes a debug log to a fixed RAM buffer — the patched emulator dumps it on fatal fault
  • Defeated the dynarec breakpoint problem: Debug.GDBWaitForConnection = yes forces cache flush so breakpoints compile fresh

Live guest-RAM reads

  • Read guest memory via /proc/<pid>/mem from the host — verified the stub planted correctly, WAD copied byte-for-byte
  • Caught: truncated WAD ("PNAMES not found"), off-screen framebuffer address, the hung download

Key insight: every fix in this talk came from reading the actual machine state, not guessing. The emulator turned a black box into an observable system.

What's next — Dreamcast game research

From the browser to games

The browser proved the Dreamcast is a viable research target — exotic but tractable. The same toolchain (IDA SH-4, Flycast GDB stub, live RAM reads) applies to any Dreamcast GD-ROM.

Dreamcast games that go online share the same attack surface: no ASLR, no DEP, 16 MB flat memory, plaintext network protocols. But they add their own parsers: game-state serialization, lobby messages, spell/item data.

Phantasy Star Online

Sega's flagship online RPG (2001). Players reported that casting certain magic spells would crash the console — specific spell combinations in specific situations.

Spell data is serialized, sent over the network, and parsed by the game engine. A consistent crash on valid-but-edge-case input is the signature of a memory corruption bug in the spell/effect parser.

An ideal target: network-reachable, user-triggerable, and the crash is already documented by the community.

Takeaways

  • EOL design flaws outlive the company. A dead update server + no sandbox = permanent RCE for whoever answers the DNS. This is still the trust model of countless shipping IoT devices.
  • A write primitive can be a reliability tool. We turned an unbounded memcpy into deterministic code placement to beat a random stack — the bug fixed the other bug.
  • The exploit is the easy part. 80% of the work was transport, memory layout, video, and timing on a constrained black box. Getting DOOM to actually run took longer than getting code execution.
  • Instrument everything. A patched emulator + live RAM reads turned guesswork into engineering. Every fix came from reading the machine state.
  • Old platforms are great teachers. No ASLR/DEP/sandbox lets you learn exploitation fundamentals without fighting mitigations. The constraints are real but different — architecture, memory, and tooling, not policy.
