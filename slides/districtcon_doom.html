DOOM on a Dreamcast Browser

Unauthenticated remote code execution → native SH-4 DOOM
on the PlanetWeb Internet Browser v3.0 (2001)

DistrictCon · Junkyard track — dead hardware, live exploits

Christopher Hernandez

The target

  • Sega Dreamcast · PlanetWeb Internet Browser v3.0 (USA)
  • Hitachi SH-4 @ 200 MHz, little-endian
  • 16 MB main RAM · no MMU (flat memory) · no ASLR · no DEP
  • PersonalJava 1.1.8 VM + the Eden service framework
  • Network: 56k modem / broadband adapter → eden.planetweb.com

Why it's interesting

A 24-year-old networked appliance: a privileged Java runtime that auto-downloads and runs code from a server that no longer exists — so we can be that server.

Goal: get native code execution and run real id-tech DOOM — no jailbreak, no physical mods, just the network.

Two ways in

Design flaw → privileged Java

The Eden service-subscription chain hands server-controlled code to a runtime with no sandbox. 100% reliable, zero memory corruption.

Memory corruption → native SH-4

Native parsers (mail, images) have classic unbounded copies. Gets us off the JVM and onto the bare metal.

We use both: the design flaw as a reliable foothold and transport, the overflow as the pivot to native code. DOOM needs the metal.

Bug #1 — Eden service-subscription RCE CRITICAL · unauth

boot → Eden login → discovery URL (server XML) → subscribe → service JAR URL (server-controlled)
→ download over plaintext HTTP → read Main-Class → JarClassLoader.newInstance().run()

  • No SecurityManager is ever installed — loaded code is fully privileged
  • No JAR signature check · all comms plaintext HTTP
  • Jar-Files: manifest attr pulls more jars from arbitrary URLs
  • Server domain is dead → answer DNS for eden.planetweb.com → ship a JAR the console runs

Result: arbitrary privileged code on boot. Our foothold + data pipe. No crash, no corruption.

The Java→native bridge

One choke point exposes the SH-4 to Java:

NativeSystemInterface.sendCommand(int cmd, Object, Object)

  • Reverse-engineered all 27 command codes from the 4.4 MB SH-4 image
  • 300 openURL · 1003 vmuPutFile · 111 setSecurityFile (no-op)

cmd 100 — setRawDeviceID

memcpy(dst=0x8C29ABE6 [fixed], src=byte[], len=attacker)

No bound check. A linear write of attacker bytes to a fixed, known address. Remember this — it wins us the demo later.

The lay of the land — 16 MB, flat, no ASLR

Constraints that shape everything

  • 16 MB total — doom+WAD (~3.8 MB) must be tetris'd around a live browser
  • No ASLR — every address above is fixed boot-to-boot… except the stack
  • The stack location varies ±32 KB at trigger time → the reliability problem
  • The stub lands at a fixed spot in browser BSS via the memcpy primitive
  • WAD, engine, heap, log: all at addresses we chose to avoid overlap

Bug #2 — native MIME stack overflow HIGH · PC control

  • Mail client handler fn_application_x_dreamcas @ 0x8C04669C
  • A MIME attachment's name= parameter is copied unbounded into a 64-byte stack buffer
  • Overwrites the saved return address (PR) → full PC control
  • Byte-safe: copy stops on 0x00 / 0x20 / 0x22 — payload avoids them

An email that, when opened, runs our SH-4 code. This is the pivot from JVM to bare metal.

…but “overwrite PR and win” turned out to be the easy 20%.

Bonus bugs — the image parsers DoS

An in-browser fuzzer (served mutated images via unique URLs to beat the VMU cache) found three native decoder hangs:

GIF LZW

Minimum code size = 12 (valid 2–8) → decoder spins → whole browser freezes. 35-byte PoC.

Progressive JPEG

SOF2 with component count Nf=5 (max 4) → component-array OOB → hang.

GIF dimensions

65535 × 65535 logical screen → allocation/loop hang.

All reachable by a served image alone — no Java needed. Strong ACE leads; shipped as DoS findings.

Challenge #1 — the overflow was a coin flip

  • Fixed payload, fixed saved-PR value… yet ~50% of opens crashed
  • The stack location at trigger time varies by ~32 KB (browser call depth / JVM state)
  • A hardcoded PR → an on-stack NOP sled is a gamble: sometimes lands in the sled, sometimes clobbers a live browser pointer → 0x60036003 fault loop
  • No clean jmp @r15 / mov r15,rN;jmp pivot gadget exists in the image

The wall

~50%

reliable, at best.
Unacceptable for a live demo.

The key insight

Don't fight the random stack.
Put the code at a fixed address using the primitive we already control.

Java (reliable) → setRawDeviceID(100) plants our stub at 0x8C29ADE8
Overflow → saved-PR = 0x8C29ADE8  ·  no sled, no stack dependence

The unbounded write primitive (a “bug”) becomes our reliability mechanism. Deterministic every time.

Challenge #2 — don't kill the browser while planting

  • The fixed memcpy dest overlaps an IM-list head pointer at DST+0x46
  • Zero it → the interface manager dereferences null → crash
  • We can't read it back to preserve it (getRawDeviceID returns only 8 bytes)

Fix

Write a harmless fake node there whose teardown-unlink targets scratch memory, and plant last (after staging) to minimize the window. Browser stays alive; mail UI keeps working.

Challenge #3 — getting 3.8 MB onto 16 MB of RAM

Can't carry it in the email

  • The mail attachment parser is O(n²) — a big body is hopeless
  • So: Java stages doom.bin + WAD over HTTP into one heap byte[]
  • Native stub scans the heap for a magic tag, copies it into place

The emulated link fights back

  • A single 3.4 MB read hangs the browser's net thread → “planetweb offline”
  • PersonalJava 1.1.8: no setRequestProperty (HTTP Range), close() won't break a hung read
  • Fix: chunked transfer — 32 KB pieces via ?start=N&len=M, only URL.openStream
  • Write the magic last → scanner only ever finds a complete blob

Challenge #4 — actually making DOOM run

Memory tetris

WAD @ 0x8C450000, engine @ 0x8CC00000, heap @ 0x8C790000 — non-overlapping in 16 MB. Trim audio lumps from the WAD (keep PNAMES/textures/levels or R_Init dies).

Video

No KOS — reuse the browser's live video. Live-read FB_R_SOF1 for the real framebuffer (hardcoding it rendered off-screen → “frozen browser”). 2× scale 320×200 → 640×480.

Timing

Drive the loop off SH-4 TMU2 free-running counter — no interrupts needed.

Boot state

Clear SR.BL, mask IRQs, inherit the browser's machine state, then jump in. Sound disabled (lumps trimmed).

How we debugged a black box

  • Built Flycast from source with the GDB stub + a custom patch that dumps SH-4 fault context (epc/PR/BL/r15) on every exception
  • DOOM writes a debug log to a fixed RAM buffer; the patched emulator dumps it on a fatal fault
  • Read guest RAM live via /proc/<pid>/mem — verified the stub planted, the WAD copied byte-for-byte, where init stalled
  • That's how we caught: truncated-WAD “PNAMES not found”, off-screen framebuffer, the hung download

Every fix in this talk came from reading the actual machine state, not guessing.

Takeaways

  • EOL design flaws outlive the company. A dead update server + no sandbox = permanent RCE for whoever answers the DNS.
  • A write primitive can be a reliability tool. We turned an unbounded memcpy into deterministic placement to beat a random stack.
  • The exploit is the easy part. 80% of the work was transport, memory layout, video, and timing on a constrained black box.
  • Instrument everything. A patched emulator + live RAM reads turned guesswork into engineering.

No ASLR/DEP/sandbox is a great teacher — and a cautionary tale for every shipping appliance today.
